Overview

Autonomous NPC AI is a solo Unity project in which an NPC finds its own way around a level and decides for itself what to do. It patrols the level, spots energy blocks and goes to collect them, and stops to investigate when it hears a sound.

I built it in two stages over 8 weeks. The first stage was the movement and a simple A* pathfinding on a square grid, where the NPC moves up, down, left and right. The second added the senses and the decision-making on top. The level has walls that can be switched on and off, collectible energy blocks and sound emitters, plus an on-screen debug panel that shows the NPC's current path.

My role

This was a solo project, so I built every part of it:

  • Implemented a simple grid-based version of A* pathfinding in C#, plus a path follower that moves the NPC from waypoint to waypoint.
  • Built a vision sense: a view cone with range, angle and wall line-of-sight checks, so the NPC only sees what it should.
  • Built a hearing sense that picks up nearby sound emitters.
  • Wrote the decision-making controller, a priority-based state machine with three states: Collect, Investigate and Patrol.
  • Added an energy system: energy drains over time, and if it runs out the NPC stops moving. Collecting energy blocks refills it, which gives the NPC a reason to go after them.
  • Created debug tools: an on-screen panel showing path length, the current waypoint and the target position, and keyboard controls for turning walls on and off.

How it works

Sense, decide, move

I split the AI into three layers, each made of separate scripts:

  1. Sensing: VisionSense and SoundSense collect information about the world.
  2. Deciding: the NPC Controller chooses what the NPC should do.
  3. Moving: the pathfinding and movement scripts carry it out.

No layer needs to know how the others work internally.

Priorities, not randomness

The NPC always follows the same order:

  1. Collect: if it can see an energy block, it goes for it. It keeps going even if the block leaves its view, as long as the block is still there.
  2. Investigate: if it hears a sound and isn't collecting anything, it goes to check the source.
  3. Patrol: if nothing else is happening, it moves between patrol points.

Once it collects the block or reaches the sound, it clears that target and goes back to patrolling.

Seeing properly

An object only counts as seen if it's within range, inside the view cone, and not behind a wall. An early bug let the NPC detect blocks through walls. Because vision lived in its own script, I could fix it there without touching the controller or the movement code.

Handling walls that change

Walls can be switched on and off while the game runs. The path doesn't recalculate when that happens. Instead, the NPC uses its vision to spot the new wall and work its way around it as well as it can.

Getting A* to work

Pathfinding was the hardest part of the project. For a long time the NPC wouldn't follow its path properly, or kept heading to the middle of the map instead of its target. Working through tutorials helped me understand where my implementation was going wrong, and I fixed it step by step.

Reusing the AI

To test how modular the system really was, I added a second NPC. It runs on exactly the same scripts, with only some settings changed in the Inspector.

What I learned

The biggest lesson was the value of keeping AI modular. Splitting vision, hearing, decisions and movement into separate scripts made each part easier to debug and to reuse. On a large team, it would also let different programmers work on senses, decisions and movement at the same time without breaking each other's code.

I also learned how hard pathfinding is to get right. A small mistake can send the NPC somewhere completely different, so being able to see the path in the debug panel was essential.

Next I would:

  • Fix the jittery movement that happens when an NPC gets close to an energy block.
  • Recalculate the path when walls change, so the NPC doesn't have to rely only on its vision to get around them.
